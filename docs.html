Authentication

Direct PropData requests use an API key in the x-api-key header. Keep production credentials server-side. RapidAPI subscribers authenticate with the credentials RapidAPI provides in its generated requests.

Direct REST
curl "https://propdata-api-worker.sales-fd3.workers.dev/v1/property?country=EE&address=..." \
  -H "x-api-key: $PROPDATA_API_KEY"
Never put a direct PropData production key in URLs or browser bundles. Use server-side environment variables or secrets.

Address → property

Resolve an official Estonia address into the property and cadastral context beneath it. The resolver can return canonical address identity, coordinates, parcel resolution, available geometry and source provenance.

GET/v1/property?country=EE&address=...Address resolution
ParameterStatusDescription
countryrequiredSet to EE.
addressrequiredFull Estonian address. Official formatting is preferred.
Example

Parcel → property

Resolve a canonical Estonia parcel identity through the same property route. Today the production resolver is verified against PropData's canonical Estonia parcel ID such as ads_ky.10290090.

GET/v1/property?country=EE&parcel=ads_ky.10290090Canonical parcel identity
ParameterStatusDescription
countryrequiredSet to EE.
parcelrequiredCanonical Estonia parcel ID returned by PropData.
Example
GET /v1/property?country=EE&parcel=ads_ky.10290090
Human cadastral-code lookup is being promoted separately. The underlying record preserves the native cadastral code (for example 48001:001:0526), but the current production parcel resolver is verified against the canonical ads_ky... identity. We will not document a human cadastral code as a guaranteed direct lookup until that resolver path is promoted.

Coordinates → parcel

Resolve latitude and longitude directly into the matching Estonia parcel context. This is the cleanest geospatial workflow because it does not force an address-string match.

GET/v1/property/by-location?country=EE&lat=...&lng=...Point-in-property resolution
ParameterStatusDescription
countryrequiredSet to EE.
latrequiredLatitude in decimal degrees.
lngrequiredLongitude in decimal degrees.
Example
GET /v1/property/by-location?country=EE&lat=58.12511901&lng=25.34680635
Verified live. The example coordinate resolves to EE:MAARUUM:CADASTRE:ads_ky.10290090 with polygon geometry and coverage_status=live_enriched.

Response semantics

PropData's core contract is source-aware. Do not treat a 200 response as proof that every optional property fact exists.

match_level

How the input was resolved, such as address_to_parcel, parcel_id or coordinate.

coverage_status

Whether the relevant property layer is live and what level of source coverage was available.

parcel_resolution

Whether the property request successfully attached parcel identity.

provenance / source

Source context that allows applications to understand where the property fact came from.

Fail-closed facts. If a source does not publish or verify a property fact, PropData keeps it unavailable instead of manufacturing a value.

Sources & provenance

Estonia is built on official national address and cadastral source systems from Maa- ja Ruumiamet (Estonian Land and Spatial Development Board). PropData maintains the ingestion, normalization, identity resolution, spatial processing and developer contract above those systems.

01 · SOURCEOfficial Estonia records

ADS addresses, property objects, cadastral identity and geometry.

02 · NORMALIZEPropData graph

Stable IDs, explicit relationships, source context and country-aware semantics.

03 · DELIVERProduction API

REST delivery with authentication, quotas and predictable response contracts.
