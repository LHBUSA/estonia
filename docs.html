Seven workflows. Six REST routes.

The Estonia product is intentionally simple at the HTTP layer while exposing several distinct developer workflows. Address, native cadastral and canonical parcel lookup share the same property route but behave as different identity inputs.

PROPERTYAddress → property

Official ADS address resolution with address identity, hierarchy, related objects and parcel attachment.

PROPERTYCadastral code → property

Use Estonia's native katastritunnus directly, for example 29601:014:0290.

PROPERTYCanonical parcel → property

Resolve a PropData canonical ID such as ads_ky.10477142.

LOCATIONCoordinates → property

Point-in-polygon resolution without forcing an address text match.

Authentication

Direct PropData requests use an API key in the x-api-key header. Keep production credentials server-side. RapidAPI subscribers use the credentials RapidAPI inserts into marketplace requests.

Direct RESTserver-side only
curl "https://propdata-api-worker.sales-fd3.workers.dev/v1/property?country=EE&parcel=29601:014:0290" \
  -H "x-api-key: $PROPDATA_API_KEY"
Never place a direct PropData key in a URL, browser bundle, public repository or client analytics.

Canonical parcel → property

Every materialized parcel has a stable PropData canonical identity. This is useful when you persist a resolved property and want deterministic re-fetching later.

GET/v1/property?country=EE&parcel=ads_ky.10477142Canonical property identity
GET /v1/property?country=EE&parcel=ads_ky.10477142

Canonical lookup and native cadastral lookup converge on the same underlying property record. The native identifier remains visible in estonia.native_identity.cadastral_code.

Estonia-native identity

PropData keeps the identifiers that matter in Estonia instead of replacing them with made-up U.S.-style fields.

cadastral_code

Native Estonian katastritunnus, for example 29601:014:0290.

ads_oid

ADS source-object identity such as CU00140341 or a building object OID.

adob_id

ADS object-version/source-record identity retained by the normalized graph.

adr_id

Official ADS address identity attached to normalized address records.

code_address

Official structured ADS code-address value where present.

ehr_code

Building Register code where the building ↔ parcel source relationship supplies it.

global_*_id

Stable PropData identity across address, object and parcel layers.

source_revision

Source revision context attached to the normalized Estonia parcel layer.

Graph-scale note: the current Estonia property-object layer contains 2.44M+ objects, while object ↔ address relationships exceed 10.27M. These counts describe different graph layers and are not interchangeable with parcel polygon counts.

Building ↔ parcel relationships

Estonia's parcel enrichment now attaches the official building relationship graph where available. Each linked building can carry ADS identity, object class/status, coordinates, related addresses, ETak identifiers and an EHR building code.

building_relationships.count

Total linked buildings found for the native cadastral parcel.

ehr_code

Building Register identity from the source relationship extract when present.

relationship_priority

Source relationship priority retained from the building ↔ cadastral relation.

addresses[]

Official addresses explicitly linked to that building object.

Response semantics

PropData is source-aware. A successful HTTP response is not permission to assume every optional fact exists.

match_level

How the input resolved: address_to_parcel, address, cadastral_code, parcel_id or coordinate.

coverage_status

Explicit state for the relevant data layer, such as live_enriched or address-only coverage.

parcel_resolution

Whether an address request successfully attached a parcel.

source / provenance

Source context travels with the property fact instead of disappearing during normalization.

Fail-closed facts: if the official source does not publish or verify a field, PropData keeps it unavailable rather than fabricating a value.

Sources & provenance

PropData Estonia is built from official national address and cadastral source systems from Maa- ja Ruumiamet (Estonian Land and Spatial Development Board), including ADS address/object identity and official building ↔ cadastral relationships. PropData maintains the ingestion, normalization, identity resolution, spatial processing and developer contract above those source systems.

01 · SOURCEOfficial Estonia records

ADS addresses and objects, national cadastral identity, geometry and source relationships.

02 · NORMALIZEPropData property graph

Stable IDs, native identifiers, explicit relationships, lifecycle and provenance.

03 · DELIVERProduction API

REST delivery with authentication, quotas, coverage semantics and additive enrichment.
